An input type that allows Smelter to receive streams over RTMP.

Smelter exposes an RTMP endpoint after you register the input by sending a [`register-input` request](/http-api/routes#register-input).

| Media Type | Supported Codecs |
| :--- | :--- |
| **Video** | `H.264`, `VP8`\*, `VP9`\* |
| **Audio** | `AAC`, `Opus`\* |

<small>_\* E-RTMP feature._</small>

The RTMP connection is configured using the following parameters:
- The Smelter server address
- The configured RTMP port - defaults to `1935`, configurable via [`SMELTER_RTMP_SERVER_PORT`](/deployment/configuration#smelter_rtmp_server_port) 
- The id the input was registered under (used as the RTMP application name)
- The registered `stream_key`

Most RTMP clients accept connection parameters in the form of a URL.\
Format: `rtmp[s]://<smelter_ip>:<port>/<input_id>/<stream_key>`


<Aside>
To enable RTMPS (RTMP over TLS/SSL), configure the following environment variables:
- [`SMELTER_RTMP_TLS_CERT_FILE`](/deployment/configuration#smelter_rtmp_tls_cert_file) — path to the TLS certificate file
- [`SMELTER_RTMP_TLS_KEY_FILE`](/deployment/configuration#smelter_rtmp_tls_key_file) — path to the TLS private key file
</Aside>

## Usage

To use an RTMP server input you must register it first. You can do it by sending a request like this:

<CollapsibleDetails summaryTitle='Example request' open>

```http
POST: /api/input/example/register
Content-Type: application/json

{
  "type": "rtmp_server",
  "stream_key": "mykey"
}
```
</CollapsibleDetails>

See [HTTP Routes](/http-api/routes#inputs-configuration) documentation to learn more about managing inputs.

Once the RTMP server input is registered and Smelter is listening on the configured URL, you can push a stream to it using any RTMP client (e.g. OBS, FFmpeg) — for the example above, stream to `rtmp://127.0.0.1:1935/example/mykey`.

## Reference

<CollapsibleDetails summaryTitle='Type definition' open>
```tsx
type RtmpServerInput = {
  type: "rtmp_server";
  stream_key: string;
  required?: bool;
  decoder_map?: DecoderMap;
  side_channel?: SideChannel;
  ingest_mode?: "realtime" | "offline";
  buffer?: InputBuffer;
}
```
</CollapsibleDetails>

Parameters for registering an RTMP server input.

## Properties

### stream_key
The RTMP stream key a publisher must use to connect to this input.

- **Type**: `string`

---

### required
Determines if the input stream is essential for output frame production. If set to true and the stream is delayed, Smelter will postpone output frames until the stream is received.
- **Type**: `bool`
- **Default value**: `false`

---

### decoder_map
Assigns which decoder should be used for media encoded with a specific codec. Currently, more than one decoder is supported only for `H264`.

- **Type**: [`DecoderMap`](#decodermap)

---

### side_channel
Enable [side channel](/http-api/side-channel/overview) publishing for this input. The
external consumer reads decoded frames / audio from a Unix socket created under
`SMELTER_SIDE_CHANNEL_SOCKET_DIR`.

- **Type**: [`SideChannel`](#sidechannel)

---

### ingest_mode
Defines if the stream is real-time.

- **Type**: `"realtime" | "offline"`
- **Default value**: `"realtime"`
- **Supported values**:
  - `"realtime"` - Input stream is treated as real-time, media processing synchronizes with the pace the stream is received.
  - `"offline"` - Assume that the source is a file or other static resource. It can push media faster than real time and it is the server's responsibility to throttle it.

---

### buffer
Input buffer configuration.

- **Type**: [`InputBuffer`](#inputbuffer)
- **Default value**: `{ desired_ms: 2000, min_ms: 1000, max_ms: 5000 }`


## DecoderMap
Maps codecs to the provided decoders.

<CollapsibleDetails summaryTitle='Type definitions' open>
```tsx
type DecoderMap = {
  h264?: 'ffmpeg_h264' | 'vulkan_h264';
};
```
</CollapsibleDetails>

### Properties

#### h264
H264 decoder configuration.

- **Type**: `'ffmpeg_h264' | 'vulkan_h264'`
- **Default value**: If available `vulkan_h264` will be used, otherwise `ffmpeg_h264`
- **Supported values**:
  - `"ffmpeg_h264"` - Software decoder based on FFmpeg.
  - `"vulkan_h264"` (<Badge text="Required feature: gpu-video" variant="note" />) - Hardware-accelerated decoder. Requires GPU that supports Vulkan Video decoding.

## SideChannel
Per-track side channel configuration. See the [Side Channel overview](/http-api/side-channel/overview) for details on how decoded data is exposed and consumed.

<CollapsibleDetails summaryTitle='Type definition' open>
```tsx
type SideChannel = {
  video?: bool;
  audio?: bool;
  delay_ms?: f64;
};
```
</CollapsibleDetails>

### Properties

#### video
Publish decoded RGBA video frames for this input on the side channel.

- **Type**: `bool`
- **Default value**: `false`

#### audio
Publish decoded PCM audio batches for this input on the side channel.

- **Type**: `bool`
- **Default value**: `false`

#### delay_ms
Side channel delay in milliseconds. Frames are buffered for this duration ahead of when the queue consumes them, so the side-channel subscriber receives them early and has roughly this much time to process before the frame is due.

- **Type**: `f64`
- **Default value**: `0`

## InputBuffer
Buffer a live input keeps between the live edge of the stream and playback. A larger buffer adds latency, but tolerates more delivery jitter and network stalls.

A number value is a shorthand for `{ desired_ms: <number> }`. Values that are not provided are derived from the provided ones and the protocol defaults.

<CollapsibleDetails summaryTitle='Type definition' open>
```tsx
type InputBuffer = f64 | {
  desired_ms?: f64;
  min_ms?: f64;
  max_ms?: f64;
};
```
</CollapsibleDetails>

### Properties

#### desired_ms
Buffer the input aims to keep, in milliseconds. At the start it should buffer at least that much media before producing the first chunk.

- **Type**: `f64`
- **Default value**: `2000`

#### min_ms
Lower range of what is considered stable state. If the buffer is smaller than this value, then media will be slightly "stretched" so the buffer converges on the desired value.

- **Type**: `f64`
- **Default value**: `1000`

#### max_ms
Upper range of what is considered stable state. If the buffer is larger than this value, then media will be slightly "squashed" so the buffer converges on the desired value.

- **Type**: `f64`
- **Default value**: `5000`
